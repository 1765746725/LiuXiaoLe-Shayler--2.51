## 〇、v29d 诊断回顾

### 做了什么

用 v28 最优架构（QK-Norm + GQA 4KV + 2层 ckpt + LR=3e-4），分别只用 CCI3 和 Industry 单源跑 500 步，测试跨源梯度冲突假说。

### 结果

| 测试 | ema@500 | 最佳点 | 结论 |
|------|:---:|:---:|------|
| v28 3-source mix | 4.65 | — | 混合基线 |
| v29d CCI3 only | 4.97 | — | CCI3 信号密度不足 |
| v29d Industry only | 4.74 | **4.24 @ step 380** | lit_emo 是高信号数据 |

### 裁决

- **CCI3 网页文本信号密度低**，纯跑比混合更差（4.97 vs 4.65）
- **literature_emotion 是真正的高信号数据**，380 步冲到 ema=4.24
- **Industry 内部 math_stats/ai_ml 是噪声源**，文件切换时 loss 从 4.23 跳到 5.47
- **跨源梯度冲突假说修正：** 不是 CCI3 vs Industry 冲突，是低信号密度数据拖累整体收敛

### 启示

MiniMind 104M 模型效果好的原因不在架构，在数据——wiki + 百科 + 新闻 + 问答，每条 < 512 字符，信号密度远高于 CCI3 网页文本。

## 二、v30 最终配比计算

```
训练总量: 25000 steps × 128 batch × 1024 seq = 3.28B tokens

加权采样 55/40/5：
  MiniMind:  3.28B × 55% = 1.80B → 0.76B × 2.4 epoch ✓
  Industry:  3.28B × 40% = 1.31B → 0.75B × 1.7 epoch ✓
  Math:      3.28B × 5%  = 0.16B → 0.02B × 10.9 epoch（5% 步数，无害）

总计: 304 文件 · ~1.52B tokens · 平均 ~2.2 epoch
```

### 为什么是 55/40/5

从原始计划 70/25/5 调整，因为实际数据量倒挂——Industry 和 MiniMind token 量几乎相等（750M vs 755M）：

| 方案 | MiniMind epoch | Industry epoch | 评价 |
|------|:---:|:---:|------|
| 70/25/5 @ 20000 | 2.4 | 0.87 | Industry 不到 1 圈 ❌ |
| 60/35/5 @ 25000 | 2.6 | 1.5 | MiniMind 偏高 |
| **55/40/5 @ 25000** | **2.4** | **1.7** | 两边均衡 ✅ |

### 为什么是 25000 步（≈2 epoch）

- MiniMind 104M 最佳点是 2 epoch
- 我们 294M 容量更大，对知识的消化能力更强，2.4 epoch 不会过拟合
- Industry 1.7 epoch 接近 2，加上 750M tokens 多样性足够
- Math 10+ epoch 但仅占 5% 步数，稀疏穿插，不构成过拟合风险

### Industry 角色定位

v29d 证明纯文学数据 ema 能到 4.24。Industry 40% 权重包含三类数据：

1. **lit_emo（主力）** — 语言能力锚点，提供稳定的叙事/表达梯度信号
2. **math_stats** — 数学推理风格，体量小但为模型注入结构化思维模式
3. **ai_ml** — 技术精确表达，帮助模型学习代码/技术术语的使用方式

三类混合保证语言多样性，防止 MiniMind 百科数据"过冷"。

**v31 已重新训练分词器（2026-07-07），不再复用旧的 CCI3 分词器。**

| | 旧分词器 | 新分词器 (v31) |
|------|:---:|:---:|
| 文件 | `tokenizer_8k/tokenizer.json` | `tokenizer_minimind_8k/tokenizer.json` |
| 训练数据 | IndustryCorpus2 (CCI3) | **MiniMind pretrain** |
| 目标词表 | 8000 | 8000 |
| 实际词表 | **13166** (超出 65%) | **8000** (正好) |
| Fertility (MiniMind 数据) | 1.001 | **0.699** ↓30% |

**换分词器的原因：**
- 旧分词器在 CCI3 上训练，88% 词表在 MiniMind 数据中从未被使用（浪费 11.8M embedding 参数）
- `：`（全角冒号）在旧分词器中编码为 `<unk>`，破坏了 `用户：`/`小乐：` 等训练标签
- 新分词器 fertility 0.699，同样 1024 token 窗口能容纳 ~1460 字符中文（旧分词器只能 ~1024）

> 训练脚本见 `train_tokenizer_8k.py`，使用 `pretrain_t2t_mini.jsonl` 采样 10 万行训练。

### 原始数据：sft_t2t.jsonl

| 参数 | 值 |
|------|:---:|
| 文件名 | `sft_t2t.jsonl` |
| 大小 | **14 GB** |
| 总条数 | **5,109,432** |
| 中位轮数 | 2 |
| 中位消息长度 | 104 字 |
| 内容覆盖 | R语言、佛学、税法、百科、编程、通用问答… |

### 预处理（`preprocess_sft_data.ipynb`）

与训练代码分离，4 个 cell，纯标准库（不依赖 PyTorch）：

| 规则 | 说明 |
|------|------|
| 角色映射 | user→用户, assistant→小乐, system→系统 |
| 长度过滤 | 总字符 >1200 或轮数 <2 → 跳过 |
| 工具对话 | 工具调用占比 >30% → 跳过 |
| ★ 身份自曝 | 9 条正则，"我是AI助手/语言模型/ChatGPT/…"→ 整条跳过 |
| 残留检查 | 转换后扫描前 10 万条验证 |

**身份自曝正则覆盖：** 我是(你的/一款)AI助手、我是(语言模型/大模型/聊天机器人)、我是(ChatGPT/Claude/文心一言/通义千问…)、我不是(真人/人类)、我没有(真实的情感/意识)、我是一款(AI/智能助手)、我的名字叫X助手、我不能感受情感

### 训练时数据增强（`sft_v30_stage1.ipynb` Cell 5）

★ **多助手标签：** 数据中角色名始终为 `"小乐"`，`format_chat()` 编码时每个对话加权随机选标签：

| 标签 | 权重 | 示例 |
|------|:---:|------|
| `小乐：` | 50% | 小乐：嗨~今天天气不错 |
| `柳小乐：` | 30% | 柳小乐：我是柳小乐，很高兴认识你 |
| `阿乐：` | 20% | 阿乐：好啊，让我讲个笑话… |

同对话内标签一致。5M 条 × 加权随机 → 三个标签都有充足训练样本。模型学会三个称呼都是自己。

### SFT mask 策略

| token 类型 | mask | 说明 |
|------|:---:|------|
| 助手回复（小乐/柳小乐/阿乐） | 1.0 | 主训练目标 |
| 用户/系统消息 | 0.0 | 不参与 loss |
| 1→0 过渡（助手→用户标签开头 2 token） | 1.0 | 学会结束回复 |

## 十一、v30 SFT 最终结论（2026-07-06）🔴

### 表面 vs 实际

| | 表面 | 实际 |
|------|------|------|
| Loss | ema 5.0→3.59→2.66，看起来很收敛 | 模型学会用高频格式化 token 作弊降 loss |
| 梯度 | gn 0.2→1.0+，"梯度复活" | 找到了 markdown token 这条捷径，梯度信号更强 |
| 输出 | — | `#` `*` `\n` `步骤` `设计` `选择` 等格式化碎片 |

### 决定性测试

给定 `用户：你好`，模型 top-10 预测：`的`(4.52) `设`(3.50) `在`(3.30) `打`(2.83) `。`(2.66) `地`(2.59) `*`(2.58) `选`(2.47) `按`(2.33) — **`小`(id=3560) 根本不在 top-10。**

训练 10608 步后，模型不认识对话格式。

### 根因：MiniMind SFT 数据内容偏差

MiniMind `sft_t2t.jsonl`（14GB，510万条）覆盖 R语言、佛学、税法、百科、编程、通用问答…但其中大量内容是 **markdown 格式的教程/攻略/步骤说明**：

- `#` `##` `###` — 标题层级
- `*` `**` — 列表/加粗
- `步骤` `设计` `选择` `方案` — 教程高频词
- `1.` `2.` — 编号列表

这些 token 在 assistant 回复中高频出现（loss mask=1.0），模型很快发现：输出这些格式化 token 就能把 masked loss 降下来。**Loss 下降是模型在走捷径，不是学会对话。**

### 与 Base 模式坍塌的联动

Base 阶段：MiniMind pretrain 数学题过多 → 模型表征偏向数学题格式
SFT 阶段：MiniMind SFT 教程类过多 → 模型学会格式化 token 作弊

**两条路径汇合：模型既不会"理解输入"，也不会"生成对话回复"。**

### 教训

> **SFT 数据的内容分布比数量重要得多。** 510 万条如果 30%+ 是 markdown 教程，等于在训练模型写攻略，不是在训练对话。
>
> **Loss 下降 ≠ 模型变好。** 在 masked loss 下，任何高频 token（包括 `#` `*`）只要落在 mask=1.0 区域，模型就会优先学习。需要按内容类型分层监控 loss，不能只看一个数字。
>
> **数据质量检查需要内容分类。** CJK 占比、身份过滤、长度过滤都不够——还需要识别"这是对话还是教程"，在预处理阶段分类剔除。

### 认知转变

v30 刚废弃时认为根因是 MiniMind 数据质量问题，提出了换数据源、API 生成 SFT 等方案。但 MiniMind 作者用同样的数据成功了——如果数据真的"全链路不可用"，作者的模型也不会有效。v30 额外加了 Industry 污染、多助手标签等变量，不能把失败归因于 MiniMind 数据。

v31 的定位是**控制变量重试**：去掉 Industry，换随机种子，新分词器，直接在 MiniMind 原版数据上再跑一次。

### v31 Base 训练验证（2026-07-08）

| 指标 | 数值 |
|------|------|
| 训练步数 | 20000（~1.08 epoch） |
| 最终 ema | ~1.15 |
| 模式坍塌 | ❌ 无 |
| 数据质量验证 | ✅ MiniMind 原版数据可行 |

**结论：v30 失败根因确认。** 不是 MiniMind 数据质量问题——是 RoPE 维度 bug（注意力输出跨 batch 混淆）+ Industry 数据污染的组合。v31 修复 RoPE + 纯 MiniMind 数据后，Base 阶段训练质量显著优于 v30，不同 prompt 产出不同领域的连贯中文续写。

**⚠️ 已知问题：Base 阶段未做数据清洗。** Base 使用 MiniMind pretrain 数据（CCI 通用语料为主，非对话格式），虽不像 SFT 数据那样密集出现"我是AI助手"等身份声明，但科普/新闻/百科类文本中仍包含"人工智能""AI 技术""作为AI"等表述。模型在 Base 阶段已内化部分 AI 身份认知——SFT 起步 loss=1.15 即为 Base 终点。重跑 Base ~3.5 天成本过高，当前策略靠 SFT 清洗数据冲刷覆盖。**这是已知技术债，理想情况应从 Base 数据源头清洗。**

- 格式统一：身份数据 messages → conversations（user/assistant）

#### 为什么 9:1 混合有效

v4.x 失败的核心教训：身份数据占比过高（20%-80%）→ 模型崩塌或过拟合。v51 用 9:1 混合，身份数据仅占 10%：

1. **身份信号稀疏但均匀** — 每 10 条训练数据中有 1 条含柳小乐身份，模型在大量通用对话的上下文中自然吸收身份信息
2. **不会过拟合** — 10% 身份 + 90% 通用对话 → 1 epoch 后身份学习到位，但对话能力几乎无损
3. **无需特殊标签** — 统一 `user`/`assistant` 两标签，无 `system：` 扰动
